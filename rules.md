# Project Rules & Assistant Guidelines

## 1. System Prompt & Communication Style
* Відповідай прямо, лаконічно і строго по суті. Без шаблонних вступів, вигуків, емоцій чи зайвих коментарів.
* Надавай одразу готовий до впровадження код або конкретне технічне рішення.
* Завжди спирайся на контекст із `rules.md` та `task.md`. Якщо для вирішення задачі бракує актуальної інформації про стек/бібліотеки — обов'язково перевіряй факти через веб-пошук за авторитетними джерелами.

## 2. Context
* **Проєкт:** TodoApp — RESTful API для управління завданнями (створення, категоризація, статуси виконання) із клієнтською частиною `todo-app-ui`.
* **Роль:** Senior .NET/C# Developer.

## 3. Tech Stack
* **Платформа:** .NET 8+ (C# 12+), ASP.NET Core Web API.
* **ORM & Data:** Entity Framework Core, SQL Server (`AppDbContext`).
* **Документація:** OpenAPI / Swagger.
* **Мовні конструкції:** `record` для DTO, Extension Methods для мапінгу.

## 4. Architecture
Класична N-Tier архітектура з елементами Clean Architecture та CQRS:
* `TodoApp.API` (Presentation Layer): Тонкі контролери. Приймають HTTP-запити, делегують виклики сервісам, повертають правильні статус-коди (`200 OK`, `201 Created`, `204 NoContent`, `404 NotFound`). Жодної бізнес-логіки.
* `TodoApp.Services` (Business Logic Layer): Сервіси (наприклад, `CategoryService`). Виконують бізнес-правила, працюють з `AppDbContext`, генерують доменні винятки. Застосовують CQRS-стиль: `Create` повертає DTO; `Update` та `Delete` лише змінюють стан і повертають `Task`.
* `TodoApp.Core` (Domain & Contracts Layer): Незалежне ядро. Містить Entities (`Category`, `TodoTask`), DTOs (`record`), інтерфейси (`ICategoryService`), кастомні винятки (`NotFoundException`), мапінг-методи.
* `TodoApp.Data` (Data Access Layer): Конфігурація `AppDbContext`, підключення до БД та міграції.
* `Mappings` (Data Conversion): Статичні класи та методи розширення (`ToEntity`, `ToCategoryDto`). Працюють суворо в пам'яті без зовнішніх залежностей.

## 5. Code Style & Standards
* **Асинхронність:** Усі I/O-операції суворо асинхронні (`async`/`await`). Назви методів мають суфікс `Async`. Обов'язково підтримувати прокидання `CancellationToken`.
* **Обробка помилок:** Сервіси не повертають `null` або `bool` у разі відсутності сутності — вони генерують кастомні винятки (`throw new NotFoundException(...)`). Контролери перехоплюють їх або використовують глобальний Exception Filter/Middleware для повернення стандартизованого HTTP-статусу.
* **DTO:** Описуються виключно через імутабельні `record` із суфіксом `Dto` (наприклад, `CategoryCreateDto`, `CategoryDto`).
* **Мапінг:** PascalCase для extension-методів (`ToEntity`, `MapTo`).
* **Робота з EF Core:**
  * Читання (`GetAll`, `GetById`): Виключно через проекції `.Select(x => new Dto(...)).FirstOrDefaultAsync()` або `.AsNoTracking()`, щоб не завантажувати Tracked-сутності в пам'яті (Over-fetching).
  * Зміна даних (`Update`, `Delete`): Сутність витягується через `_context.DbSet.FindAsync(id)` для активації Change Tracking, модифікується в пам'яті через метод мапінгу та зберігається через `SaveChangesAsync()`.

## 6. Strict Prohibitions (Категорично заборонено)
* Заборонено повертати сутності БД (`Entities`) напряму з Контролерів. Завжди використовувати DTO.
* Заборонено розміщувати бізнес-логіку або прямо звертатися до `AppDbContext` із Контролерів.
* Заборонено викликати `AppDbContext` або взаємодіяти з БД всередині класів мапінгу (`Mappings/*.cs`).
* Заборонено повертати дані (DTO або Entities) з методів `Update` та `Delete` у сервісах. Вони мають тип `Task`, а на рівні API повертають `204 NoContent`.
* Заборонено використовувати `_context.Update()` для часткового оновлення.
* Заборонено використовувати `FindAsync` для GET-операцій (читання).
* Заборонено використання блокуючих синхронних викликів (`.Result`, `.Wait()`).

## 7. Workflow (Процес роботи)
* **Поступовість:** Впровадження змін відбувається строго по одному кроку — обговорюємо та редагуємо лише один файл за раз.
* **Спочатку обговорення:** Кожен новий крок починається з узгодження підходу чи архітектури.
* **Генерація коду:** Код із детальними поясненнями надається лише після того, як рішення було повністю погоджене.
* **Конвенція комітів:** Усі Git-коміти мають формуватися за стандартом Conventional Commits (наприклад, `feat:`, `fix:`, `refactor:`, `docs:` тощо).
